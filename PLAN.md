## 1. Objectives

- An authoritative Rust server keeping the entire world state.
- Four clients across four different engines / languages joining one server and seeing each other:

| Client | Engine | Language | Fomoxa Runtime Used | fomoxac Backend |
|---|---|---|---|---|
| unity | Unity | C# | `Fomoxa.Net` (netstandard2.1) - [fomoxa/csharp](https://github.com/fomoxa/csharp) | C# |
| godot | Godot 4.3+ | GDScript | `addons/fomoxa` addon - [fomoxa/godot](https://github.com/fomoxa/godot) | GDScript |
| unreal | Unreal Engine 5 | C++ | C library + `net.hpp` wrapper - [fomoxa/c](https://github.com/fomoxa/c) | C++ |
| kaiju | Kaiju Engine | Go | `github.com/fomoxa/go` - [fomoxa/go](https://github.com/fomoxa/go) | Go |

- Client simulates nothing: only sends inputs, receives state, and renders.
- Minimalist graphics: a plane, each player is a colored block (cube/capsule).
- Entire codec generated by `fomoxac`; runtime uses existing SDKs, no hand-written wire formats.

Out of scope: prediction, complex interpolation, collision between players, matchmaking, multiple rooms, security, automatic reconnect.

## 2. Architecture

```
 Unity (C#)    Godot (GDScript)   Unreal (C++)   Kaiju (Go)
     │               │                 │              │
     └───────────────┴──────── TCP ────┴──────────────┘
                              │
                   ┌──────────┴───────────┐
                   │  server (Rust)       │
                   │  fomoxa-net Server   │
                   │  World: fixed tick   │
                   └──────────────────────┘
```

A single tick workflow:

```
client: read keyboard → PlayerInput ──────────────▶ server: save latest input by peer
                                                   server: step World (fixed dt)
client: render per WorldSnapshot ◀────────────── server: broadcast WorldSnapshot
```

### 2.1 Key aspects of fomoxac in a multi-language setup

- `fomoxac` only reads one language per run. There is no "generate once to 4 languages": each client re-declares the models in its own language, has its own `fomoxa.toml`, and runs `fomoxac generate` separately. This is exactly the model of [fomoxa/interop](https://github.com/fomoxa/interop).
- Handshake succeeds only when the fingerprint matches, thus it is mandatory that:
  - Model names and codec names match character-by-character across all languages (message id is hashed from `<Model>.<codec>`).
  - Field order and wire types match exactly. Field names are folded (lowercase, stripping `_`, `-`, spaces) so `player_id` / `PlayerId` / `PlayerID` / `playerId` are equivalent.
- The protocol source of truth is the [protocol/PROTOCOL.md](protocol/PROTOCOL.md) file (created in Phase 1). The server's Rust model is its first implementation; all clients check against this file, not copying from one another.
- A script checks and compares `FOMOXA_SCHEMA_FINGERPRINT` in `.fomoxa/schema.json` of the server against each client - run before any real testing (§6).

⚠️ Conflict with the "no comments" convention: Go and GDScript only have ways to annotate via comment directives (`//fomoxa:model`, `# fomoxa:u32`). These lines are directives for fomoxac, not explanatory comments, and are mandatory. No other comments should be written.

## 3. Protocol (Proposed)

A single codec named `game` for all models, so that nested models (`PlayerState` in `WorldSnapshot`) always share the same codec with their parent model.

| Model | Direction | Field (in order) |
|---|---|---|
| `ClientHello` | client → server | `client_kind: u8`, `display_name: string` |
| `Welcome` | server → client | `player_id: u32`, `plane_half_size: f32`, `tick_rate: u16` |
| `PlayerInput` | client → server | `sequence: u32`, `move_x: f32`, `move_z: f32` |
| `PlayerState` | (nested) | `player_id: u32`, `client_kind: u8`, `color: u32`, `position_x: f32`, `position_z: f32` |
| `WorldSnapshot` | server → client | `tick: u32`, `players: Array<PlayerState>` |

- `client_kind`: 1 Unity, 2 Godot, 3 Unreal, 4 Kaiju - to let each block display an engine label, highlighting the cross-language nature of the demo.
- `color` is assigned by the server (RGBA u32) so that every engine renders the exact same color for the same player.
- Avoid nested `Vector3`/`Vector2` types: use flat `f32` fields. Reason: `unity-codecs` turns `Vector3` into an extern codec that fomoxac does not scan ([fomoxa/unity-codecs](https://github.com/fomoxa/unity-codecs) - "fingerprint mechanism only protects models it scans itself"), risking fingerprint mismatch with the other 3 languages. Unity constructs `new Vector3(x, 0, z)` on its side when rendering.
- `Array<PlayerState>` (array of models, not nested array) is supported by all backends - available in the `fomoxac/tests/fixtures*/` fixtures.

Server Rules (Proposed):

- Fixed simulation tick rate at 30 Hz; runtime's `tick_now()` is called every loop (~16 ms).
- Velocity is 5 units/second, `move_x`/`move_z` clamped to `[-1, 1]` then normalized if length > 1.
- Position clamped within the plane `[-plane_half_size, plane_half_size]`, `plane_half_size = 10`.
- Player is spawned when the server receives `ClientHello`, and destroyed when peer is `Disconnected`/`HandshakeFailed`.
- Broadcast `WorldSnapshot` every simulation tick. If `send` returns `Congested` then drop that snapshot for that peer (the subsequent snapshot replaces it). `Welcome` is kept and retried in the next tick until successful.
- Transport: TCP (see §9 D1).

## 4. Repository Structure (Proposed)

```
fomoxa-example-game/
├── docs.md
├── PLAN.md
├── protocol/
│   └── PROTOCOL.md                  canonical model table - source of truth
├── server/                          Rust crate
│   ├── Cargo.toml                   fomoxa-net, fomoxa-attributes
│   ├── fomoxa.toml
│   ├── .fomoxa/schema.json
│   └── src/
│       ├── main.rs                  loop: runtime tick + world fixed-step
│       ├── schema.rs                FOMOXA_MESSAGES → Schema
│       ├── world.rs                 World, step, snapshot
│       ├── models/                  annotated models
│       └── generated/               fomoxac output, committed verbatim
├── tools/
│   ├── bot/                         headless Rust client (reusing server models)
│   └── check-fingerprints.sh
└── clients/
    ├── unity/                       Unity project
    ├── godot/                       Godot project, copies addons/fomoxa
    ├── unreal/                      UE5 project + ThirdParty fomoxa module
    └── kaiju/                       Go module (go.mod beside fomoxa.toml)
```

Each client shares the same networking layout: `fomoxa.toml`, `models/`, `generated/`, `.fomoxa/schema.json`, and a thin `NetworkClient` layer consisting of: connect → send `ClientHello` when `Ready` → send `PlayerInput` every frame → synchronize block instances on scene upon receiving `WorldSnapshot` (create / update position / delete).

## 6. Verification

| Level | Method | When |
|---|---|---|
| Fingerprint | `tools/check-fingerprints.sh` compares `schema_fingerprint` with server | after each `fomoxac generate` |
| Freshly generated | `fomoxac generate --check` in each directory | before commit |
| Server logic | `cargo test` for `world.rs` | Phase 1 onwards |
| Bizarre payload | `fomoxa-inspect --schema server/.fomoxa/schema.json --message WorldSnapshot.game --hex ...` | when a client decodes incorrectly |
| End-to-end | headless bot + engine client simultaneously | each client phase |

`SchemaConflict` during Handshake is almost always caused by a mismatch in field order / wire types / model names / codec names - verify against `PROTOCOL.md` before debugging runtime.
